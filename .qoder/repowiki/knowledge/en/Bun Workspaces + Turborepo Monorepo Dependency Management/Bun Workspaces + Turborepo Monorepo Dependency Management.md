## System / Approach

The repository is a TypeScript monorepo managed with **Bun** as the package manager and **Turborepo** for task orchestration. There are no Go, Python, or Ruby dependency manifests — all third-party dependencies are declared in `package.json` files under a Bun workspace layout.

### Package Manager: Bun
- The root `package.json` pins the engine via `"packageManager": "bun@1.4.3"`, which enforces that developers use this exact Bun version (via Corepack-style resolution).
- A single lockfile at the repo root, `bun.lock`, records the resolved dependency tree across all workspaces (lockfileVersion 2, configVersion 1).
- No `.npmrc`, `.yarnrc`, or private registry configuration exists; packages are resolved from the public npm registry.

### Workspace Layout
Root `package.json` declares:
```json
"workspaces": ["web", "api", "packages/*"]
```
This creates four workspace packages:
- `web` — Next.js 16 frontend
- `api` — NestJS backend
- `packages/types` → published as `@repo/types`
- `packages/validators` → published as `@repo/validators`

Workspace packages (`@repo/types`, `@repo/validators`) are internal-only (`"private": true`, `"version": "0.0.0"`). They are consumed by other workspaces via bare specifiers like `"@repo/types": "*"` and `"@repo/validators": "*"` — Bun resolves these to the local workspace rather than fetching from npm.

### Build Orchestration: Turborepo
`turbo.json` defines tasks (`build`, `dev`, `test`, `typecheck`, `db:generate`, `db:seed`, `start`, `test:api`) with explicit `dependsOn` and caching rules. Root scripts delegate to Turbo (`"build": "turbo run build"`, etc.).

### Versioning Strategy
- Internal workspace packages use `"*"` as the specifier when referenced by other workspaces, meaning they always resolve to whatever version is defined in the local workspace's `package.json`. This avoids publishing internal packages to npm.
- Third-party dependencies use a mix of caret ranges (`"^11.1.27"`, `"^5"`, `"^8.16.3"`) and exact versions (`"next": "16.2.12"`, `"react": "19.2.7"`, `"@prisma/client": "7.10.0"`, `"@prisma/adapter-pg": "7.10.0"`, `"prisma": "7.10.0"`). Prisma packages are pinned to an exact version across `dependencies` and `devDependencies`.
- Shared tooling (TypeScript, Vitest) is kept consistent across workspaces: `typescript: ^6.0.3`, `vitest: ^4.1.10`.

### Vendoring
No vendored dependencies exist. `node_modules` directories appear only under each workspace (e.g., `api/node_modules`, `web/node_modules`) and under the root — these are generated by Bun and not committed (see `.gitignore` patterns). There is no `vendor/` directory or equivalent.

### Private Registries / Auth
No `.npmrc`, `bunfig.toml`, or environment variables for private registries were found. All dependencies come from the public npm registry.

### Lockfile & CI
- `bun.lock` is the authoritative source of truth for installed versions.
- `skills-lock.json` appears to be a separate lockfile used by the agent-skill system under `.agents/skills/`, unrelated to npm/Bun dependencies.
- `.github/workflows/ci.yml` runs the CI pipeline but does not contain custom dependency-update automation (no Dependabot, Renovate, or similar bot configuration was detected).

## Key Files
- `package.json` — root workspace manifest, declares Bun as package manager, workspaces, and shared dev deps
- `bun.lock` — Bun lockfile pinning every transitive dependency
- `turbo.json` — Turborepo task graph, cache, and env propagation
- `api/package.json` — NestJS + Prisma + Supabase API dependencies
- `web/package.json` — Next.js + React + Supabase client dependencies
- `packages/types/package.json` — internal `@repo/types` package manifest
- `packages/validators/package.json` — internal `@repo/validators` package manifest (depends on `zod`)

## Architecture & Conventions
1. **Single-package-manager monorepo**: Bun workspaces provide flat dependency resolution; there is no per-workspace lockfile.
2. **Internal packages via `@repo/*` scope**: Shared types and validators live in `packages/` and are consumed with `"*"` specifiers, keeping them out of the public npm registry.
3. **Exact versions for framework/runtime packages**: Next.js, React, Prisma, and adapter packages are pinned to exact versions to avoid drift between API and web.
4. **Caret ranges for libraries**: Utility libraries (NestJS, RxJS, jose, pg, zod) use caret ranges to allow compatible updates.
5. **Turborepo owns the build graph**: Every workspace exposes standardized scripts (`build`, `dev`, `test`, `typecheck`) so Turbo can parallelize and cache them.
6. **Prisma codegen is uncached**: `db:generate` has `cache: false` in `turbo.json` because it writes to `src/generated/**`, ensuring fresh schema artifacts.

## Conventions & Constraints
- **Use Bun**: The `packageManager` field in the root `package.json` constrains the runtime to `bun@1.4.3`; adding new dependencies should go through `bun add` so `bun.lock` stays in sync.
- **Declare dependencies in the owning workspace**: Runtime dependencies belong in the workspace `package.json` that uses them; shared tooling lives at the root.
- **Internal packages must stay private**: Both `@repo/types` and `@repo/validators` set `"private": true` and `"version": "0.0.0"`, preventing accidental publication.
- **Consume internal packages with `"*"`**: Cross-workspace references use the wildcard specifier, which forces resolution against the local workspace rather than npm.
- **Pin framework/runtime packages exactly**: Next.js, React, and Prisma ecosystem packages are pinned to exact versions to keep the full stack deterministic.
- **No vendoring**: Dependencies are fetched from npm into `node_modules`; nothing is checked in under a vendor directory.
- **No private registry configured**: There is no `.npmrc` or Bun registry override; all packages are sourced from the public npm registry.
