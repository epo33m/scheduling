## What system/approach is used

The repository uses a minimal, file-based configuration approach with no dedicated configuration library:

- **Runtime env vars** are loaded via `dotenv` (`api/src/env.ts`) and consumed directly from `process.env`.
- **Supabase local stack** is configured through the standard `supabase/config.toml` generated by the Supabase CLI.
- **Monorepo task orchestration** passes environment variables through Turborepo's `globalPassThroughEnv` in `turbo.json`.
- There is no schema validation, type-safe config loader, feature-flag framework, or secrets manager — configuration is intentionally flat and developer-facing.

## Key files and packages

- `.env.example` — template of required environment variables for local development.
- `api/src/env.ts` — dotenv bootstrap that loads `.env` at repo root and allows an `api/.env` to override it.
- `api/src/main.ts` — NestJS entry point; reads `PORT` from `process.env` with a default of `3001`.
- `supabase/config.toml` — full Supabase local-stack configuration (API, DB, auth, storage, realtime, studio, etc.).
- `turbo.json` — monorepo task definitions plus `globalPassThroughEnv: ["DATABASE_URL", "DIRECT_URL"]`.
- `package.json` — top-level scripts wrapping `turbo run`, `supabase start/stop`, and Prisma commands under `api/`.

## Architecture and conventions

### Dotenv layering
`api/src/env.ts` calls `config({ path: ['.env', '../.env'] })`. The comment documents the intended precedence: a single `.env` at the repo root is shared by the API runtime, Prisma migrations, and the seed script; an `api/.env` can override keys because dotenv keeps the first value found per key. `main.ts` imports this module before bootstrapping NestJS so all services see the same `process.env`.

### Environment variable contract
`.env.example` declares three variables:
- `DATABASE_URL` — pooled Postgres connection used by NestJS at runtime.
- `DIRECT_URL` — direct Postgres connection used by Prisma migrations.
- `PORT` — HTTP port for the NestJS server (defaulted to `3001` in code).

The values in `.env.example` point at `127.0.0.1:54422`, which matches the Supabase local DB port declared in `supabase/config.toml` (`[db].port = 54422`).

### Port convention
All local service ports are shifted from their defaults into the `544xx` range so this project's Supabase stack coexists with another ERP Supabase instance on the same machine. Observed mappings:
- Supabase API: `54421`
- Supabase DB: `54422`
- Supabase Studio: `54423`
- Local SMTP: `54424`
- Pooler: `54429`
- Analytics: `54427`
- Shadow DB: `54420`
- NestJS API: `3001` (from `.env.example`)

### Secrets handling
Secrets are not committed to the repo. The only committed secret-like file is `.env.example`, which contains placeholder connection strings. `supabase/config.toml` uses the `env(VAR_NAME)` substitution syntax for sensitive values (e.g. `openai_api_key`, `auth_token`, S3 credentials), deferring actual secret resolution to the Supabase CLI.

### Monorepo env propagation
`turbo.json` explicitly whitelists `DATABASE_URL` and `DIRECT_URL` via `globalPassThroughEnv`, ensuring these variables reach child tasks (`db:generate`, `db:seed`, `test:api`). Other process environment variables are not automatically passed through Turborepo.

### No typed config layer
There is no Zod/Yup/Joi schema, no `ConfigService` abstraction, and no config validation at startup. Values are read as raw strings from `process.env` and coerced inline (e.g. `Number(process.env.PORT ?? 3001)`). This means missing or malformed env vars surface as runtime errors rather than structured validation failures.

## Conventions and constraints

- **Single source of truth for env**: `.env.example` documents every required variable; developers copy it to `.env` before running locally.
- **Dotenv load order**: `api/src/env.ts` must be imported before any module that reads `process.env`; `main.ts` does this as its first import.
- **Port naming**: local Supabase services use the `544xx` port range to avoid collisions with other local Supabase projects.
- **Secrets policy**: no secrets are committed; `.env.example` contains only example connection URIs, and `supabase/config.toml` references secrets via `env(...)` placeholders.
- **Turborepo env whitelist**: only `DATABASE_URL` and `DIRECT_URL` are guaranteed to propagate to child tasks; adding new env vars requires updating `globalPassThroughEnv` in `turbo.json`.
- **No runtime config validation**: the codebase does not enforce presence or shape of env vars at startup — absence falls through to Node.js defaults or `undefined`.
