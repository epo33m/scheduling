The module is a NestJS `@Module` (`auth.module.ts`) that wires together three layers:
- Token verification: `SupabaseTokenService` uses `jose` to locally verify ES256-signed Supabase access tokens against a remote JWKS fetched at startup via `createRemoteJWKSet(supabaseJwksUrl())`; issuer and audience are validated.
- Identity resolution: `AuthGuard` (global) extracts the Bearer token, verifies it, then looks up the employee by lower-cased email in Prisma; missing or inactive rows throw `ForbiddenException`, otherwise the resolved `SessionEmployee` is attached to `request.employee`.
- Authorization: `RolesGuard` runs after `AuthGuard` and checks the `employee.role` against roles declared via the `@Roles(...)` decorator.

Metadata-driven configuration lives in `auth-metadata.ts` (`PUBLIC_ROUTE_KEY`, `ROLES_KEY`) consumed by the `@Public` and `@Roles` decorators in `auth.decorators.ts`. Route-level identity injection is provided by `CurrentEmployee` in `current-employee.decorator.ts`, which reads `request.employee` typed as `AuthenticatedRequest` (defined in `authenticated-request.ts`). Supabase endpoint constants (`supabaseUrl`, `supabaseIssuer`, `supabaseJwksUrl`) live in `supabase.ts` and derive all URLs from `process.env.SUPABASE_URL`. Dependency direction is one-way outward: this module depends on `../prisma/prisma.service` and `@repo/types`, but exposes only `SupabaseTokenService`, `AuthGuard`, and `RolesGuard` via `exports`.
